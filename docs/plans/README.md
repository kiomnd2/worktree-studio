## 작성 규칙

새 기능 플랜은 `docs/plans/{기능-이름}.md`로 만들고 위 목록에 한 줄 추가합니다. 아래 순서를 따릅니다.

1. **머리말**: 버전, 작성일, 상태 한 줄
2. **배경과 목표**: 지금 문제, 목표, 성공 기준(확인 가능한 문장)
3. **범위**: 하는 것 / 하지 않는 것
4. **아키텍처**: 흐름을 텍스트 다이어그램으로, 기존 모듈과의 연결
5. **기능 명세**: 표(기능 · 동작 · 구현 메모 · 단계 · 상태)
6. **핵심 흐름**: 사용자가 따라가는 번호 순서
7. **변경 파일** 또는 **데이터 모델**: 실제 경로 기준
8. **로드맵**: 단계별 내용과 완료 기준
9. **리스크와 대응**: 표(등급 · 리스크 · 영향 · 대응)
10. **결정 사항**: `결정: 내용` + 이유 한두 줄

### DB 변경이 있는 플랜

테이블·컬럼·인덱스·제약·공통코드를 추가·변경·삭제하거나 기존 데이터를 옮겨야 하면, 플랜과 별도로 `docs/plans/{기능-이름}.db.md`를 만든다. 플랜 본문에는 바뀌는 테이블과 요약만 적고 이 문서로 링크한다. 조회만 바뀌면 만들지 않는다.

담을 것:

1. **요약**: 바뀌는 테이블 목록과 용어 확인 결과 한 줄 (`용어사전 확인: 컬럼 N개 중 표준 N, 고침 N, 등록 요청 N`)
2. **테이블별 변경**: 표(구분 추가·변경·삭제 · 논리명 · 컬럼 물리명 · 타입·길이 · NULL · 기본값 · 설명)
3. **인덱스·제약**
4. **DDL 또는 Liquibase changeset 초안**: 이미 적용된 changeset은 고치지 않고 새로 더한다.
5. **데이터 이관**: 기존 데이터 채우기·옮기기 SQL과 되돌리는 방법
6. **용어 확인**: 새로 쓰거나 바꾸는 이름마다 erd-vibe 용어사전과 맞춘 결과를 표로 적는다(논리명 · 쓸 이름 · 판정: 표준 / 표준으로 고침(원래 이름) / 등록 요청함 · 도메인). 실제로 찾아본 결과만 적고, 승인이 남은 단어·용어·ERD 변경 요청은 표 아래에 따로 모은다. 사전을 확인하지 못했으면 그렇다고 적는다.
7. **영향 범위**: 매퍼·엔티티·API·화면

이 저장소(Worktree Studio) 자체의 SQLite 변경은 `server/src/db.ts`나 각 모듈의 `CREATE TABLE`·`ALTER TABLE` 마이그레이션 코드와 대상 테이블을 적는다. 용어사전 확인 대상은 아니다.

### 상태 표기

- 기능 명세와 로드맵에 `상태` 칸을 두고 `✅ 완료`, `🚧 진행 중`, `⬜ 예정`, `➖ 보류`, `🔀 변경됨` 중 하나를 씁니다.
- 계획과 다르게 구현했으면 `🔀 변경됨`으로 두고 **구현 결과** 절에 무엇이 왜 달라졌는지 적습니다. 원래 계획 문장은 지우지 않습니다.
- 구현이 끝나면 머리말의 상태와 위 목록을 함께 고칩니다.

### Claude가 읽기 좋게

- 코드 위치는 `server/src/runner.ts`처럼 저장소 기준 경로로 씁니다. 함수·테이블·API는 백틱으로 감쌉니다.
- 수치 기준(포트 범위, 줄 수, 시간)은 문장에 묻지 말고 숫자로 적습니다.
- 그림 대신 텍스트 다이어그램이나 목록을 씁니다.
