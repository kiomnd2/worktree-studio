서버 로그로 쿼리를 감시하고 최적화까지 잇는 기능

띄운 BE 서버가 찍는 SQL 로그를 실시간으로 모아, 자주 불리거나 무겁거나 N+1로 반복되는 쿼리를 찾아 보여준다. 고를 때만 실행 계획을 받고, 고치는 일은 Claude가 제안하고 사용자가 승인한다.

배경과 목표

지금은 화면이 느리면 로그 탭을 손으로 훑어 같은 쿼리가 몇 번 나왔는지 세고, SQL을 복사해 DB 도구에서 실행 계획을 따로 본다. 서버 로그와 DB 연결은 이미 이 도구 안에 있으니 그 사이를 잇는다.

지금 있는 재료

  • runner.ts의 pushLine이 서버 출력을 한 줄씩 받아 비밀값을 가린 뒤 3000줄까지 들고 있다.
  • dbquery.ts의 runQuery가 세션 DB에 읽기 질의를 롤백 트랜잭션으로 실행한다. EXPLAIN은 이미 읽기로 본다.
  • claude.ts의 db_query 도구와 approvals.ts의 dbwrite 승인 카드가 있다.

빠진 것

  • 로그에서 SQL을 알아보는 코드가 없다. 로그는 3000줄에서 잘리므로 나중에 훑어서는 앞부분을 놓친다.
  • Oracle과 MSSQL은 실행 계획을 받는 문장이 isReadOnly에 걸려 막힌다.
  • Claude가 서버 로그나 쿼리 통계를 볼 도구가 없다.

목표

  • 화면 하나를 눌렀을 때 어떤 쿼리가 몇 번, 몇 행씩 나갔는지 바로 보인다.
  • 의심 쿼리를 골라 버튼 한 번으로 실행 계획과 인덱스 정보를 본다.
  • 고칠 쿼리는 근거(통계, 계획, 매퍼 위치)를 붙여 Claude에게 넘기고, 수정과 DDL은 승인 뒤에만 반영된다.

범위

이번에 하는 것

  • MyBatis, Hibernate, p6spy 로그에서 SQL 추출
  • 쿼리 모양별 집계와 규칙 기반 경고
  • 집계를 SQLite에 보관(도구를 다시 켜도 남음)
  • RightPanel BE 서버 영역의 쿼리 탭
  • 엔진별 실행 계획 조회(Oracle 우선)
  • Claude 최적화 요청 버튼과 조회 도구
  • 매퍼 SQL 로그를 기본으로 켜는 환경값 넣기

하지 않는 것

  • 자동 수정, 자동 인덱스 생성
  • 운영 DB 감시
  • DB 쪽 통계(pg_stat_statements, V$SQL) 수집. 이후 검토
  • Node ORM(Prisma, Sequelize 등) 로그. 2차
  • 파라미터가 들어간 예시 SQL의 저장

실행 계획

explainQuery(c, sql, params)는 isReadOnly를 통과한 SELECT만 받고, 엔진별로 계획 문장을 감싸 한 연결·한 트랜잭션에서 실행한 뒤 롤백한다. ? 자리에는 로그에서 잡은 파라미터 값을 넣는다.

엔진방법주의
OracleEXPLAIN PLAN SET STATEMENT_ID = :id FOR … 다음 SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY(NULL, :id, 'TYPICAL'))두 문장이고 PLAN_TABLE에 쓰므로 지금 경로로는 막힌다. 전용 경로를 둔다. 리터럴로 넣은 계획은 바인드 변수 계획과 다를 수 있다고 화면에 적는다. 인덱스: ALL_INDEXES, ALL_IND_COLUMNS, 행 수: ALL_TABLES.NUM_ROWS.
PostgreSQLEXPLAIN (FORMAT JSON) …. 원하면 ANALYZE를 붙여 실제 실행(롤백).ANALYZE는 실제로 돌리므로 버튼을 따로 둔다. 인덱스: pg_indexes, 행 수: pg_class.reltuples.
MySQL·MariaDBEXPLAIN FORMAT=JSON …인덱스: information_schema.STATISTICS.
MSSQLSET SHOWPLAN_XML ON 다음 질의, 끝나면 OFFSET이 쓰기 단어라 전용 경로가 필요하다. 질의는 실행되지 않는다.

핵심 흐름: 느린 화면에서 수정 제안까지

  1. 서버 띄우기 평소처럼 띄우면 매퍼 SQL 로그가 켜진 채로 시작한다.
  2. 측정 구간 잡기 쿼리 탭에서 초기화를 누르고 미리보기에서 느린 화면을 한 번 연다.
  3. 의심 쿼리 보기 호출 수 순으로 보면 N+1 경고가 붙은 selectDetail이 40번 나간 것이 보인다.
  4. 실행 계획 행을 눌러 상세를 열고 실행 계획을 받는다. 테이블 전체 읽기와 인덱스 목록이 함께 나온다.
  5. Claude에게 넘기기 "최적화 요청"을 누르면 근거가 대화로 들어간다. Claude가 매퍼 XML을 찾아 JOIN 한 번으로 바꾸는 diff와 인덱스 DDL을 제안한다.
  6. 승인과 확인 코드 수정은 평소처럼, DDL은 승인 카드로 반영한다. 다시 초기화하고 같은 화면을 열어 호출 수가 줄었는지 본다.

로드맵

step-1 · 3~4일

추출, 집계, 쿼리 탭

MyBatis와 Hibernate 추출기, 모양 묶기, 경고 규칙, SQLite 보관, 쿼리 탭, 매퍼 로그 기본 켜기. 이 단계는 찾아서 보여주기만 한다.

완료 기준 KEA BE를 따로 설정하지 않고 띄워 화면 하나를 열면, 그 화면이 낸 쿼리가 모양별 호출 수와 행 수로 보이고 반복 조회에는 N+1 표시가 붙는다. 도구를 다시 켜도 집계가 남아 있다.

step-2 · 2~3일

실행 계획

Oracle 전용 경로 먼저, 이어서 PostgreSQL, MySQL, MSSQL. 인덱스와 행 수를 함께 보여준다.

완료 기준 쿼리 상세에서 버튼 한 번으로 Oracle 실행 계획과 관련 인덱스가 나오고, DB에는 아무것도 남지 않는다.

step-3 · 2일

Claude 연계

최적화 요청 버튼과 server_queries, db_explain 도구.

완료 기준 요청 버튼을 누르면 Claude가 해당 매퍼 XML 위치와 근거를 짚은 수정안을 내고, DDL은 승인 카드로만 올라온다.

리스크와 대응

리스크내용대응
높음 로그가 안 나옴매퍼 패키지를 못 찾거나 프로젝트가 다른 로깅 설정을 쓰면 기본 켜기가 효과가 없다. 프로젝트마다 로그 형식도 다르다.쿼리 탭이 비어 있으면 넣은 환경값과 찾은 패키지를 보여주고 직접 고칠 수 있게 한다. 추출기는 형식별로 나눠 하나씩 붙인다.
높음 로그가 SQL로 덮임기본으로 켜므로 모든 BE 서버 로그에 SQL 줄이 크게 늘고, 3000줄 보관이 금방 차서 오류 줄이 밀려난다. 서버 도구도 느려질 수 있다.로그 탭 SQL 줄 숨기기 토글. 실패 요약(failureExcerpt)은 SQL 줄을 빼고 고른다. 글자 검사로 먼저 거르고, 모양 수 상한, 1초 묶음 전송, 5초 묶음 저장.
중간 계획이 실제와 다름리터럴을 넣은 계획은 바인드 변수로 실행될 때 계획과 다를 수 있다.화면에 적어 두고, PostgreSQL은 ANALYZE 선택지를 둔다. Oracle V$SQL 기반 실제 계획은 이후 검토.
중간 경고 오탐의도한 반복 조회나 배치 조회에도 N+1이 붙는다.표시만 하고, 쿼리 모양별로 경고 숨기기를 둔다.
낮음 파라미터 노출예시 SQL에 개인정보가 들어간다.이미 maskSecrets를 거친 줄만 쓴다. SQLite에는 값을 뺀 모양과 수치만 저장하고, 예시 SQL은 메모리에만 둔다.
낮음 PLAN_TABLE 권한Oracle 계정에 PLAN_TABLE이 없거나 권한이 없다.오류를 그대로 보여주고 필요한 권한을 안내한다.

결정 사항

집계 보관: SQLite

도구를 다시 켜도 집계가 남는다. 값을 뺀 모양과 수치만 저장하고, 워크트리를 정리할 때 함께 지운다.

매퍼 로그 켜기: 기본으로 켬

BE 서버를 띄우면 따로 설정하지 않아도 쿼리 탭이 채워진다. 서버 실행 대화상자에서 끌 수 있고, 로그 탭에는 SQL 줄 숨기기를 둔다.

엔진 순서: Oracle 먼저

KEA 프로젝트가 Oracle이라 가장 먼저 쓴다. 전용 경로가 필요해 2단계 공수가 가장 크다.

고치는 방식: 제안과 승인만

자동 수정은 넣지 않는다. 코드는 평소 대화 흐름으로, DDL은 dbwrite 승인 카드로만 반영한다.
